# 适配说明：为什么这三处必须对齐

本文记录 `config/folksu.conf` 里每个值是怎么来的，方便日后换版本时自查。

## 1. 版本号：`KSU_VERSION = 30000 + 提交数`

`FinaSU/kernel/Kbuild`：

```make
KSU_GIT_VERSION := $(shell cd $(GIT_ROOT) && $(GIT) rev-list --count HEAD)
KSU_VERSION=$(shell expr 30000 + $(KSU_GIT_VERSION))
ccflags-y += -DKSU_VERSION=$(KSU_VERSION)
```

两条推论，直接决定构建方式：

- **不能删 `.git`，也不能用 `--depth=1`**，否则 `rev-list --count` 拿不到完整历史，Kbuild 会退化成 `KSU_VERSION=16`，管理器必然不认。
- **必须切到与管理器配套的 tag**。实测 `v1.0.4` 的提交数是 2960：

```bash
$ git clone --bare --filter=blob:none https://github.com/LyraVoid/FinaSU.git
$ git -C FinaSU.git rev-list --count v1.0.4
2960                     # → KSU_VERSION = 32960
```

而管理器发布包叫 `FinaSU_v1.0.4_32960-release.apk`，`versionCode=32960`，两者吻合。

## 2. 协议版本：`KERNEL_SU_UAPI_VERSION = 6`

`FinaSU/uapi/supercall.h`（v1.0.4）：

```c
static const __u32 KERNEL_SU_UAPI_VERSION = 6;
```

注意这跟半年前的 FolkSU 时代**不一样**：参考工程
[zy071114-design/ace6-gki-6.6-fengchi-folksu](https://github.com/zy071114-design/ace6-gki-6.6-fengchi-folksu)
绑的是 `v0.1.0-beta3`、`KSU_VERSION=32787`、`UAPI=5`。混用会直接判定不兼容，所以脚本里 `UAPI` 和 `TAG` 是成对校验的。

## 3. 管理器签名：证书长度 + DER 的 SHA-256

内核侧 `kernel/Kbuild` 把两个变量编进 `apk_sign`：

```make
ccflags-y += -DEXPECTED_SIZE=$(KSU_EXPECTED_SIZE)
ccflags-y += -DEXPECTED_HASH=\"$(KSU_EXPECTED_HASH)\"
# 未定义时默认 0x033b / c37106…（上游 KernelSU 官方签名）
```

`kernel/manager/apk_sign.c` 解析 APK 的 v2/v3 签名块，取出第一张证书的 DER 字节，比长度、比 SHA-256：

```c
#define FINASU_TRUSTED_SIZE EXPECTED_SIZE      // 未定义第二个签名槽时
#define FINASU_TRUSTED_HASH EXPECTED_HASH
```

所以只要把**目标 APK 的证书**算出来喂进去，内核就只认这个管理器。`scripts/apk_cert.py` 做的就是这件事（纯标准库解析 APK Signing Block，v2/v3 都支持）：

```
$ python3 scripts/apk_cert.py FinaSU_v1.0.4_32960-release.apk --shell
FOLKSU_CERT_SIZE="0x103"
FOLKSU_CERT_HASH="f7cecef261a422eb70f7cb63272ec28c28c2b29856e51ba5ad229935ddc1d833"
FOLKSU_MANAGER_VERSION="32960"
```

> 补充：FinaSU 官方发版时会把自己的 release 密钥写进**第二个**签名槽
> （`KSU_EXPECTED_SIZE2/HASH2` + `KSU_SECOND_SIGNATURE_RELEASE=1`），
> 所以源码里默认那对值是上游 KernelSU 的证书。我们直接占第一个槽，
> 语义等价且少一层判断。

## 4. 为什么不用 FinaSU 自带的 `kernel/setup.sh`

它里面是：

```sh
test -d "$GKI_ROOT/KernelSU" || git clone https://github.com/tiann/KernelSU
```

——克隆的是**上游 tiann/KernelSU**，不是 FinaSU 自己（留下 fork 时的旧代码）。照它跑会得到一个"FinaSU 的外壳 + 上游内核代码"的混合体，版本号和 UAPI 全对不上。因此本仓库按它**同样的挂载方式**自己做：

```sh
ln -sfn ../KernelSU/kernel drivers/kernelsu
printf '\nobj-$(CONFIG_KSU) += kernelsu/\n' >> drivers/Makefile
sed -i '/^endmenu/i source "drivers/kernelsu/Kconfig"' drivers/Kconfig
```

另外 `kernel/include/uapi` 在仓库里是软链 `../../uapi`，指向仓库顶层的 `uapi/`；在 Windows 上（`core.symlinks=false`）会被检出成普通文件，脚本里做了检测与重建。

## 5. 为什么关掉 SUSFS

- `FinaSU/kernel/Kconfig` 里没有任何 `SUSFS` 相关项（只有 `KSU / KSU_DEBUG / KSU_DISABLE_MANAGER / KSU_DYNAMIC_MANAGER / KSU_DISABLE_POLICY / KSU_X86_PATCH_SYSCALL_DISPATCHER`）。
- `susfs4ksu` 的 `10_enable_susfs_for_ksu.patch` 是给老结构 `kernel/core/*.c` 写的，FinaSU 已经重排成 `kernel/feature|policy|supercall/*`，`patch -F3` 只能打进去一部分。
- 上游脚本用 `|| true` 吞掉失败，结果就是"配置里写着 `CONFIG_KSU_SUSFS=y`、日志里说打了补丁，实际没有对应代码"。这种包最坑人，所以这里直接不做，并在 defconfig 里写 `CONFIG_KSU_SUSFS=n`。

FinaSU 自己的隐藏能力（Folk-Mount / NoMount / SELinux 隐藏 / AVC 日志伪装）不依赖 SUSFS 补丁，管理器里按需开即可。

## 6. 编译后的回读校验

`scripts/folksu.sh` 的 `folksu_verify` 直接读编译日志：

```
-- KernelSU version: 32960                      # 必须等于管理器 versionCode
-- KernelSU Manager signature size: 0x103       # 必须等于 CONFIG 里的 cert size
```

再对 `Image` 做 `grep -a <cert_hash>`，确认哈希字符串真的被编进了只读数据段。
任何一项不符就 `exit 1`，不产出刷机包——避免"刷完才发现管理器不认"。

## 7. 复现验证

```bash
# 只跑集成与三元组校验，不编译（会真克隆 FinaSU）
bash scripts/build.sh --check
```

输出应包含：

```
· 内核侧 KSU_VERSION=32960（目标管理器 32960）
· 内核侧 KERNEL_SU_UAPI_VERSION=6（管理器期望 6）
· 信任管理器签名：size=0x103 sha256=f7cecef261a422eb…
```

## 8. 6.12 编译踩坑记录（按发现顺序）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | `找不到 .../work/common/arch/arm64/configs/gki_defconfig` | 解压时先建 `common/` 再 `mv .kx/* common/`，套成 `common/<顶层目录>/arch` | 单层归档直接改名成 `common` |
| 2 | `Baseband-guard setup.sh 执行失败` + `curl 404` | `github.com/<repo>/raw/master/...` 对默认分支为 `main` 的仓库 404 | 用 `raw.githubusercontent.com/.../main/setup.sh` |
| 3 | `gendwarfksyms: ... dwarf_get_units failed: no debugging information?` | 设备 defconfig 开着 `CONFIG_DEBUG_INFO_COMPRESSED_ZSTD`，`scripts/Makefile.debug` 会给 rustc 加 `-Zdebuginfo-compression=zstd`，而 `rust/core.o`、`helpers/helpers.o` 要过 gendwarfksyms | defconfig 追加 `CONFIG_DEBUG_INFO_COMPRESSED_NONE=y` 并 `# ..._ZSTD is not set` |
| 4 | `gendwarfksyms: is_definition_private: ... 'invalid .debug_line section'` | ubuntu-22.04 的 elfutils/libdw 0.186 解析不了 clang19 的 DWARF5 行表（需 ≥ 0.188） | runner 换 `ubuntu-24.04`；`build.sh` 里加 libdw 版本预检 |
| 5 | `'uapi/app_profile.h' file not found`（先） | 上游 `kernel/include/uapi` 是指向 `../../uapi` 的软链，CI 检出后未生效 | `folksu.sh` 把顶层 `uapi/` **物化复制**到 `kernel/include/uapi` |
| 6 | 同上错误仍在（后） | FinaSU `Kbuild` 的 `ccflags-y += -I$(KSU_KERNEL_DIR)/include` 在「软链挂载 + `O=out`」下没作用到 `core/` 子目录对象 | 把 `-IKernelSU/kernel -IKernelSU/kernel/include` 注入 `KCFLAGS`，全树可见 |

> 第 3、4 条是「6.12 + Rust + MODVERSIONS(gendwarfksyms)」这条链上的两个独立雷点；
> 不要试图用 `CONFIG_GENDWARFKSYMS=n` 绕过 —— 那会退回 genksyms，符号 CRC 算法变化，
> `vendor_dlkm` 的模块会因 CRC 不匹配全部加载失败。

## 9. 刷机前必读：LKM 与内置 KSU 不能混

FinaSU 有两种 root 形态，**内核要对应着编**：

| 你的机器 | 内核要 | 说明 |
|---|---|---|
| 之前用管理器「LKM 安装」/ 修补过 `init_boot` | `builtin_ksu=false`（`CONFIG_KSU` 不设） | root 由 `init_boot` 里的 `kernelsu.ko` 在开机时 insmod，内核里不能再有一份 |
| 全新未 root，想一次刷完 | `builtin_ksu=true` | KSU 编进内核，内核直接接管；`init_boot` 必须是原厂 |

两者混用（内核自带 KSU + `init_boot` 里也有 `kernelsu.ko`）的典型现象就是
**停在开机 logo、连开机动画都不出**：`ksuinit` 去加载 `kernelsu.ko` 失败，init 卡在第一阶段。

### 卡 logo 的自救顺序（A/B 设备）

1. `fastboot --set-active=b` + `fastboot reboot`（另一个槽如果还是原厂，直接活）
2. 刷回刷机前备份的 boot：`gunzip boot_backup_*.img.gz` → `fastboot flash boot_a boot_backup_*.img`
3. 官方固件包里的 `boot.img`：`fastboot flash boot_a boot.img`

> 只刷 `boot` 不会清掉 `init_boot` 里的 LKM root；要换回内置 KSU 方案时，
> 得**先把 `init_boot` 刷回原厂**，否则刷完还是卡 logo。
